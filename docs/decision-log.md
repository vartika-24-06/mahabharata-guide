- Dropped self-hosted embedding + re-ranker models (originally chosen for full hybrid search in v1). Reason: measured real memory against the actual 5,578-passage corpus at ~703MB, over Render's free 512MB even after ONNX+int8 quantization (~13% reduction, not enough). Moved to an external embeddings API (our own key) + Supabase pgvector instead of a bigger host or cutting hybrid search from v1.
- Re-ranking deferred to v2 entirely, not just switched off by default. Reason: any self-hosted transformer model reintroduces the same memory problem; bringing it back needs its own hosting decision (external API or paid host), not a setting.
- Switched the build-time embeddings provider from Gemini (`gemini-embedding-2`) to OpenAI (`text-embedding-3-small`). Reason: Gemini's free tier caps at 1,000 embedding requests/day (not per-minute as first assumed) - would take ~6 days to embed the full 5,578-passage corpus. Enabling billing to lift that cap required a disproportionate minimum prepaid top-up (~3,000 INR) versus the real cost. OpenAI's text-embedding-3-small costs ~$0.07 for the whole corpus (~3.3M tokens) with a proportional ~$5 minimum top-up, and supports truncating to the same 768 dimensions via its `dimensions` parameter, so the Supabase schema didn't need to change. Any rows already pushed with Gemini embeddings had to be truncated first - different embedding models are not comparable in the same vector search.

Also observed the classifier returned the same 0.90 confidence on every one of 6 test questions regardless of difficulty - CONFIDENCE_THRESHOLD (0.6) is effectively dead code against this model, since confidence never varies enough to cross it. Worth re-checking if the threshold mechanism is worth keeping at all, or testing against Anthropic/Gemini to see if they calibrate differently.
